## 六、潜在风险点

1. **AGPL 合规边界**：本次只迁移"实践模式"，未复制源码。若未来要引入 FSRS 具体算法实现，必须先做许可证合规评估（可考虑按公开论文独立实现，或确认上游提供双许可）。
2. **文档门禁的维护成本**：`verify_docs_consistency.py` 锁死三个当前态数字；每次发布改产物体积、每次加测试改步数，都需同步更新 README，否则门禁红。这是**刻意的设计**（AGENTS.md 要求同提交更新），但会增加发布流程负担。
3. **测试布局门禁的关键词表是白名单**：只拦明确跨域（calibration/redteam），多域共有词（graph/ocr/api）不拦——这是为了避免误报，代价是对"新型错位"覆盖不全。
4. **边界测试不锁具体系数**：只锁有限性/单调性/区间，因此 A2 调参导致的具体数值变化不会被抓到；这依赖既有的 `ParameterCalibrationTests`（1e-9 对拍）另行覆盖。
5. **设备真机验证仍缺**：Android/HarmonyOS 手势回归因无设备在线跳过；本次迁移未触碰端侧代码，风险低，但真机链路的完整性仍未在本轮验证。
6. **源项目深读的报告偏差**：三路 Agent 报告中的部分数字（如"55 唯一门禁名"、步数口径）与实测不符，均已以目标项目实际文件为准复核后才落地；报告仅作线索，不作事实源。
